# Client UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the client UI of the Comdove mock: the launch page (`/client`) and the group grid (`/client?group=x`). It runs today on **static mock data**, with no server of any kind, and connects to the real mock server later by changing one env var.

**Architecture:** Every page reads and writes through one `DataSource` interface, never through `fetch` or `WebSocket` directly. There are two implementations:
- `mock` (the default): returns fixed mock data. **It has no server behaviour.** There are no timers, no simulated ticks or queues, and no lock logic. It hands the UI one snapshot, and the UI's own local actions do the rest.
- `server`: wraps the existing `api.ts` and `ws.ts`, for when the backend exists.

`VITE_DATA_SOURCE=mock|server` picks one. A pure reducer turns both server events and local actions into screen state. That is why switching to the real server is a config change plus a checklist (Task 9), not a rewrite.

**Tech Stack:** React 19, Vite 8, TypeScript 6, react-router-dom 7, native WebSocket, CSS Modules, and Vitest for the pure modules (reducer, auto-reply engine).

Requirements: *Comdove WhatsApp Mock Server — Hackathon PRD*. This plan is lane **C4 (Dev C)**, covering FR-04 to FR-07, FR-09, FR-10, FR-14, FR-16 to FR-18 and §7 "Client grid".
Contract: *Comdove Mock Server — API Tech Spec* §6–§7, mirrored in `README.md` and `client/src/types.ts`.
Design: *Comdove Mock UI* (Claude Design). It has two screens, **Client launch** and **Client grid**. **Two things follow the design, not the PRD, on purpose:** bubble sides (the customer's own messages on the left, Comdove's on the right, Task 7; PRD §7 says the reverse) and tile width (280px minimum, see Design tokens; PRD §7 asks for 3–4 per row).

## Global Constraints

- **UI only.** This plan builds no server and no fake server. The mock data is plain data. Anything that needs a server to happen (ticks advancing, a queue flushing, locks) is verified in Task 9 against the real server.
- **Branch `feature/client-ui`.** `feature/admin-ui` already touches `components/Tile.tsx` (+2 lines). Pull it before Task 7, or expect a conflict there. Don't edit `pages/Admin.tsx`.
- **Only `src/data/server.ts` may import `api.ts` or `ws.ts`.** Check with `grep -rn "from '../api'\|from './api'\|new WebSocket" client/src`, which should find hits only in `src/data/`.
- **`types.ts` is the contract.** The mock data uses exactly these types. If a screen needs a field the spec lacks, don't invent it.
- **Every `data-testid`:** `nav-client`, `nav-admin`, `group-{slug}`, `refused-notice`, `refused-dismiss`, `group-not-found`, `back-to-groups`, `tile-{number}`, `presence-{number}`, `unread-{number}`, `queued-{number}`, `autoreply-{number}`, `input-{number}`, `send-{number}`, `retry-{localId}`. Auto-reply testids are in Task 8. PRD §8.2 requires one on everything interactive.
- **URL-addressable groups:** `/client?group=alpha` works on a cold load (FR-14).
- **Plain WebSocket.** Tech Spec §7 gives `ws://{host}/ws` and a "standard WebSocket ping", so native `WebSocket` it is.
- **Plain and dense** (PRD §7): no avatars, no extra theming, 10 tiles on one laptop screen. Dark only, as in the design.
- **`VITE_` prefix.** Only `VITE_*` variables reach the browser. `MOCK_SERVER_URL` stays with the dev proxy.

## Decisions (answered from the two PDFs)

| # | Question | Source | Decision |
| ---: | --- | --- | --- |
| 1 | ws or socket.io? | Tech Spec §7: `ws://{host}/ws`, "standard WebSocket ping" | Native `WebSocket` |
| 2 | Does the server echo a tile's own `message.send` back? | §7: `message.new` is a "new message **for** an online tile" | **No.** The tile shows its own message the moment Send is pressed (optimistic) |
| 3 | Is an open tile told when a message is queued for it while offline? | §7: `message.new` is for **online** tiles; offline messages arrive via `queue.flush` | **No.** The `queued` count comes from the `group.claimed` snapshot and clears on `queue.flush` |
| 4 | Which business number does a tile reply to? | PRD §4: a conversation is "a pair of numbers" | The business number that wrote to the tile last; else the last one it talked to; a tile with no history uses the first from `GET /api/business-numbers`. **No picker**, as in the design |
| 5 | Can a customer's own message show ticks? | Tech Spec §3: Comdove's mark-as-read "marks the inbound message read in the tile" | **Yes, only blue ✓✓ (read).** Otherwise it shows just the time |
| 6 | Where does a locked group go? | §7: "claim refused; client returns to the launch page" | Back to `/client` with a notice |
| 7 | Can read arrive without delivered? | Tech Spec §5: yes, after a reconnect | Ticks rank `sent < delivered < read` and never step back |
| 8 | Crashed-tab lock? | §7: 15s ping; a missed pong releases it | Nothing to build |
| 9 | Webhook URL in the top bar? | §8: server env `COMDOVE_WEBHOOK_URL`, not exposed by any endpoint | A display label from `VITE_WEBHOOK_URL`, hidden when empty |

### Task 2: The `DataSource` interface, the server adapter, the selector

**Files:**
- Create: `src/data/types.ts`, `src/data/server.ts`, `src/data/index.ts`

**Interfaces:**
- Produces: the only door to data. The pages don't know whether mock data or the server is behind it.

- [ ] **Step 1: Interface**

```ts
// src/data/types.ts
import type { BusinessNumber, ClientEvent, Group, ServerEvent } from '../types'

export type ConnectionState = 'mock' | 'connecting' | 'open' | 'reconnecting' | 'closed'

export interface GroupConnection {
  send(event: ClientEvent): boolean   // false = not sent (socket not open)
  close(): void                       // releases the group lock on the server
}

export interface DataSource {
  listGroups(): Promise<Group[]>
  listBusinessNumbers(): Promise<BusinessNumber[]>
  connectGroup(
    group: string,
    handlers: { onEvent(e: ServerEvent): void; onState(s: ConnectionState): void },
  ): GroupConnection
}
```

Only what the client pages use goes in here. The admin page keeps using `api.ts` on its own branch.

- [ ] **Step 2: Server adapter**

`server.ts` builds on `api.ts` and `ws.ts`:
- Call `onState('connecting')` first, then `'open'` on `onopen`.
- An **unexpected** close → `'reconnecting'`, with backoff of 1s, 2s, 4s, capped at 10s. `ws.ts` re-sends `group.claim` on open.
- An explicit `close()` sets a flag so it doesn't reconnect, then calls `onState('closed')`.
- `send()` returns `false` while the socket isn't open. **Don't queue silently.** The tile shows "not sent" with a retry instead (Task 7). A message that quietly goes out 30 seconds later confuses a tester more than a visible failure does.
- **The StrictMode double-connect:** in dev, React connects, closes and reconnects every effect. If the second `group.claim` reaches the server before the first socket's close, the tester's own tab is refused. Delay a new `group.claim` until the previous socket for that group has fired `onclose`.

- [ ] **Step 3: Selector**

```ts
// src/data/index.ts
import { mockData } from './mock'
import { serverData } from './server'
export const data = import.meta.env.VITE_DATA_SOURCE === 'server' ? serverData : mockData
```

In `.env.example`, set `VITE_DATA_SOURCE=mock`, with a comment to switch it to `server` once the backend is up on `MOCK_SERVER_URL`.

### Task 4: The group session reducer

**Files:**
- Create: `src/session/reducer.ts`, `src/session/reducer.test.ts`

**Interfaces:**
- Consumes: `ServerEvent` from `types.ts`, plus local actions.
- Produces: the only place group state changes. It is pure, so the mock and the server look the same to it.

- [ ] **Step 1: State and actions**

```ts
export interface UiMessage extends ChatMessage {
  pending?: 'sending' | 'failed'        // optimistic sends only
  localId?: string                      // until the server's wamid is known
}
export interface UiTile { number: string; online: boolean; history: UiMessage[]; queued: ChatMessage[] }

export interface SessionState {
  phase: 'connecting' | 'ready' | 'locked'
  order: string[]
  tiles: Record<string, UiTile>
  connection: ConnectionState
}
export type Action =
  | ServerEvent
  | { type: 'local.send'; localId: string; from: string; to: string; body: string; sent: boolean }
  | { type: 'local.retry'; localId: string; sent: boolean }
  | { type: 'local.presence'; number: string; online: boolean }
  | { type: 'local.read'; number: string; peer: string }
  | { type: 'local.connection'; state: ConnectionState }
```

- [ ] **Step 2: Rules**

| Action | Effect |
| --- | --- |
| `group.claimed` | `phase='ready'`, **replace** all tiles (a reconnect re-sends the full state) |
| `group.locked` | `phase='locked'` (the page redirects, Task 6) |
| `message.new {to, message}` | append to `tiles[to].history`, deduplicated by `wamid` |
| `queue.flush {number, messages}` | append in order (deduplicated), `queued = []` |
| `message.status {wamid, status}` | update that message **only upwards**: `sent < delivered < read`. A `read` with no `delivered` before it is fine (Decision 7) |
| `local.send` | append an outgoing message right away (Decision 2), with `pending: sent ? undefined : 'failed'` |
| `local.retry` | clear `failed` if it is now sent |
| `local.presence` | flip `online` |
| `local.read` | raise that peer's unread incoming messages to `read`, so the badge clears at once. On the server, `chat.read` makes it real; the rank rule keeps the later server status from undoing it |

- [ ] **Step 3: Selectors**

```ts
unread(tile)        // incoming (to === tile.number) with status !== 'read'
peers(tile)         // business numbers in this tile's history, newest first
onlineCount(state), totalQueued(state)
```

The tile is the customer's phone:
Sides follow the Comdove Mock UI design:

- **Comdove's** messages (`to === tile`): on the **right**, `--out-bg` green bubble. Above the text, a small mono label with the sender, e.g. **Sales**. The label only appears when the tile's history has more than one business number, so single-peer tiles stay clean.

- **Comdove's:** time plus tick. `sent` ✓ grey, `delivered` ✓✓ grey, `read` ✓✓ blue.
- **The customer's own:** time only, **plus blue ✓✓ when Comdove has read it** (Decision 5).

Other rules:
- Bubbles are at most 82% wide, with 12.5px/1.35 text.
- Queued messages stay out of the chat. The header pill counts them until `queue.flush`.
- Auto-scroll to the bottom only when the user was already within 40px of it.

- [ ] **Step 3: Composer**

As in the design: just the input and Send, **no "Reply to" picker**. A reply goes to the business number that wrote to the tile last, else the last one it talked to, else the first registered one for an empty tile (Decision 4).

- Enter sends. The text is trimmed; empty input is ignored; the draft clears after sending.
- The draft lives in the tile's own `useState`, so typing doesn't re-render the other tiles.
- **Offline:** the input and Send are disabled, and Send sits at opacity 0.45.

"Read when the chat is opened" (FR-06): every chat in a grid is always visible, so "opened" means the tester engages with it. When the input gains focus, or the chat is clicked while unread > 0, call `markRead(n, peer)` for each peer with unread messages. The badge clears at once (`local.read`).

### Task 8: Auto-reply (FR-10)

**Files:**

- [ ] **Step 1: Engine (pure)**

```ts
export function decideReply(cfg: AutoReplyConfig, incoming: ChatMessage, tile: string): string | null
```

- [ ] **Step 2: Loop guard**

- [ ] **Step 3: Queued messages after a reopen**

- [ ] **Step 4: Settings**
